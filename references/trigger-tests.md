# 触发测试集（Trigger Tests）：20 条真实口语路由验证

> 用途：description 改动后（或每次交付前）跑路由验证——**最容易翻车的地方不是内容而是路由**：该触发时不触发、不该触发时乱触发。
> 判定：命中率 = (正确触发的应触发条数 + 正确拒绝的应拒绝条数) / 20。**< 90%（<18/20）回改 description，不许交付。**

## 一、怎么跑

```
1. 把 20 条 prompt 逐条喂给"技能选择"环节（不加载任何技能正文，
   只看 frontmatter 的 name+description 够不够做出正确选择）
   ——这就是路由的真实工况：Agent 选技能时只读 frontmatter
2. 记录每条：期望（触发 ad-compliance-cn / 不触发）vs 实际
3. 算命中率。分两类错误分别归因：
   漏触发（应触发未触发）→ description 触发词不够覆盖该口语变体
   误触发（不应触发却触发）→ 边界交接句不够明确，触发词与相邻域重叠
4. < 90% 时按第七节的修改方法改，重跑，直到 ≥90%（上限不追求 100%，
   留 1 条容忍给边界口语——但连续两次跑出同一边界条 = 边界定义有问题，
   去改 SKILL.md 的边界句而不是硬凑 description）
```

## 二、10 条应触发（真实口语变体）

| # | prompt | 为什么该触发 |
|---|---|---|
| T1 | "这篇公众号文章明天要发，帮我看看有没有问题" | "看看有没有问题"+发布前 = 合规审查意图（无更具体意图时默认合规） |
| T2 | "这条小红书笔记会不会被限流啊，里面用了'最好用'这种词" | 极限词+平台处置风险 = 典型 |
| T3 | "我们详情页写了'全网最低价'，平台会不会判违规" | 绝对化用语+平台审核 |
| T4 | "帮我审一下这个抖音口播稿，说'三天见效'可以吗" | 功效宣称+口播稿审查 |
| T5 | "这段朋友圈文案合规吗？'稳赚不赔'这种词敢不敢用" | 收益承诺+渠道明确 |
| T6 | "投放素材上线前过一遍合规" | 发布前检查+投放素材 |
| T7 | "广告法里对'国家级'怎么规定的，我们标题想这么写" | 问法条但目的是"想这么写"= 审查意图（不是纯法律咨询） |
| T8 | "这个保健品详情页说'增强免疫力'，能发吗" | 食品功效宣称+发布判定 |
| T9 | "客户说我们的广告被平台拒了，帮我查查哪里违规" | 审核不过排查 = 合规审查 |
| T10 | "培训海报上写'包过'，这样写有没有风险" | 教培保证性承诺+风险问法 |

## 三、10 条应拒绝（相邻域，交接给别的技能）

| # | prompt | 为什么不该触发 | 应交接给 |
|---|---|---|---|
| R1 | "帮我写一篇小红书种草笔记，卖我们的面霜" | 创作意图（写内容），不是审查 | 创作类技能 |
| R2 | "广告法第九条具体原文是什么" | 纯法条咨询，无待审内容 | 通用问答（或提示可审） |
| R3 | "怎么让我们的内容被 DeepSeek 的 AI 答案引用" | AI 可见性优化，不是合规 | ai-seo-cn |
| R4 | "这个公众号文章的标题怎么写更吸引人" | 文案创作/优化 | 创作类技能 |
| R5 | "对比一下我们和竞品 A 的定价，做个分析" | 竞品/定价分析 | 分析类技能 |
| R6 | "我们的投放 ROI 一直上不去，怎么优化" | 投放效果优化，不是合规审查 | 投放/评估类技能 |
| R7 | "帮我做个广告创意方案，要 5 个方向" | 创意策划 | 创作类技能 |
| R8 | "广告法罚款一般罚多少，我们被投诉了" | 事后处置/法律咨询，不是发布前审查 | 通用问答（提示：可审查在投内容防再犯） |
| R9 | "这个 Skill 的触发词怎么调，总被误触发" | 技能路由维护（本技能的元操作，不是用本技能审内容） | 技能维护流程（跑本测试集本身算元操作） |
| R10 | "把这篇合规报告翻译成英文发给海外团队" | 翻译，报告已存在 | 翻译 |

## 四、边界条的设计意图（为什么是这 10 条）

```
R2/R8：问法条 ≠ 审内容——触发词里有"广告法"，所以这条是检验
  边界句（"只审待发布内容"）有没有压住法条咨询的
R3/R4/R6：与 ai-seo-cn/创作/投放的三角重叠区——description 的
  边界交接句（"SEO 优化走 ai-seo-cn"）在这里起作用
R9：元操作（调本技能自己）不算审内容——若这条误触发，说明
  "触发词怎么调"被"触发"一词带跑了
T7：问法条+"想这么写"= 触发——和 R2 的对照：区别在有没有
  待审意图。这对是测试集里最难的，两条都答对才算边界真清
```

## 五、命中率记录格式（每次跑完留档）

```markdown
# 触发测试 <日期> description 版本 <git commit/行号>
| # | 期望 | 实际 | 对/错 |
|---|---|---|---|
| T1 | 触发 | 触发 | ✓ |
...
命中率：__ /20 = __%
错误归因：
  漏触发：__（改法：description 加触发词 "___"）
  误触发：__（改法：边界句加 "___ 不触发"）
结论：≥90% 可交付 / <90% 回改后重跑
```

## 六、与上游 evals 的区别（别混用）

```
上游 marketingskills 的 evals.json（实测 50 文件 349 case）测的是
  技能加载后的输出质量（expected_output + assertions）
本测试集测的是路由（frontmatter 够不够让 Agent 选对技能）
两者不互相替代：路由对 + 输出差 = 技能正文问题；路由错 + 输出对 = 白干
交付标准：本测试集 ≥90%（路由）+ 输出质量用 skill-eval 的回归样例管（另议）
```

## 七、< 90% 时的 description 修改方法

```
漏触发 → 把漏掉的口语变体加进触发词（不是加同义词堆砌，是加
  "用户真实会说的"表述，从测试条里抄）
误触发 → 在 description 末尾的边界句加具体排除（"纯法条咨询不触发"
  "写文案不触发——只审不写"），排除句要写"什么情况"不是只写"什么技能"
每次只改一类问题（漏/误），改完重跑全套 20 条——
  同时改两类 = 无法归因是哪句起的作用
description 长度约束：1-1024 字符（上游 frontmatter 规范），
  超长时优先砍同义词堆砌，保留口语变体与边界句
```
